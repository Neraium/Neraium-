# Maintenance verification of the already-active contact form

This release-only policy corrects the initial-activation/maintenance distinction. It changes no Worker, route, DNS, widget, production secret, intake flag or Privacy approval. It does not authorize any deployment. Read this together with OPERATIONS.md; its initial-activation-only restrictions do not make isolated observations production-host evidence.

## Gate selection and unchanged activation safeguards

`checkConfiguration` first inspects the actual production account, configuration, routes, bindings, required secrets and temporary-production-probe absence. With both local AND remote intake/retention flags already true and no explicit transition baseline, it selects maintenance. An explicit `--activate-contact`/transition baseline always selects first activation. Missing, disabled, conflicting or unexpected remote state cannot qualify for maintenance. There is no fallback after failed maintenance verification.

Initial activation still calls `validateActivationEvidence`: fresh production-host human scenarios, original owner/receipt/retention/Privacy rules, production limiter proof and disabled-intake cleanup remain mandatory. Default freshness is unchanged. Its record validator now accepts an explicit review time for testing and checking immutable historical activation; the initial release entry point always uses the actual clock.

Maintenance is deliberately limited to this existing installation. It requires the exact active configuration and unchanged production Worker/security sources from committed baseline `80cfbb5688e9be5d5176ba9f4c9f0a2a3581f035`. Archived first activation is validated at its actual cleanup time, only as a prerequisite, never as fresh evidence. Current owner approvals, retention/copy-inventory rules and exact Privacy hash are checked separately. Configuration/security changes require a separate review, not this path.

## Fresh evidence required

No evidence is generated by installing this correction. Missing evidence must block preflight with `Contact maintenance held: fresh maintenance evidence missing`.

The operator records `.planning/contact-maintenance/evidence.json` (ignored by Git) with schema `neraium.contact-maintenance.v1`. All observations must be genuine, independently captured and confirmed by the human operator. Maximum age is seven days; each human session is at most20minutes. Never store tokens, private URLs, cookies, credentials, HAR files, full request bodies or inquiry contents in this record. The regression fixture describes the structure but is fabricated and MUST NOT be used as evidence.

Required fields and sources:

| Field | Actual source |
| --- | --- |
| `configuration_fingerprint` | `securityConfigurationFingerprint` of unchanged production config |
| `privacy_sha256`, `subject_sha256` | Approved Privacy bytes and exact unchanged production handler subject |
| `isolated.panel` | Independently retrieved authenticated server export, original isolated schema/candidate flag |
| `isolated.expectation`, `isolated.attestation` | Exact origin/session/source/package/deployment identity, independent export digest and genuine founder confirmation required by EVIDENCE-POLICY.md |
| `isolated.configuration`, `deployment_artifact_verified`, `inspected_by` | Reviewed actual enabled dedicated config, independently matched deployed artifact/version and named reviewer |
| `production` | Separate manual production checks below, real origin/sitekey/times/operator/confirmation, response semantics and diagnostic UUIDs |
| `before`, `after` | Original GET-only boundary captures before all human tests and after cleanup; production settings/version/routes/assets and enabled intake unchanged; separate Worker absent at both boundaries |
| `cleanup` | Actual dedicated host/session/sitekey, inspection time, verified access denial and Worker/widget/secrets/storage/private-file removal; production intake still enabled |
| `confirmation` | Actual operator/participation confirmation/time bound to `evidenceDigest` of the entire record excluding `confirmation` |

Cleanup booleans are `access_denied`, `worker_removed`, `widget_removed`, `secrets_removed`, `storage_removed`, `private_files_removed`, `production_intake_enabled`; each requires a genuine observation. A TTL or404 alone is insufficient. The gate also independently requires the dedicated Worker settings endpoint to return404;403/network errors fail closed. Current production settings must still match the verified session. Unknown DNS inventory is explicitly outside this route-free workers.dev operation and is NOT promoted to verified; DNS Read access is not needed for this step.

## Exact human actions after separate temporary deployment authorization

The prepared verifier needs a dedicated managed Turnstile widget limited to `neraium-contact-verifier.neraiumai.workers.dev` and its own secret. Its action is `evaluation`. Never reuse/change the production widget. Use OPERATIONS.md's exact separate Worker, two-secret upload, lifetime and cleanup process; first review the concrete public inputs and bundle. There is no reason to deploy public assets or pause intake. Agree the private link delivery channel and staffed session before generating its10-minute redemption/20-minute session credential. The base URL is `https://neraium-contact-verifier.neraiumai.workers.dev/verify`; the authenticated fragment link exists only after authorized preparation and is delivered privately.

1. On the private verifier, manually solve/run success200, exact-token replay400, reset/solve fresh synthetic failure502, reset/solve fresh recovery200, reset/solve/capture one unused token, wait at least310seconds, run expiry400 once, then validation400 and the bounded isolated429 probe. No real email is sent there. Operator independently preserves the server export/digest before revocation; founder confirms actual participation. If interrupted, preserve failure honestly and restart with a new session.
2. Separately open `https://neraium.com/contact` in a normal human browser on an operator-controlled connection. Do not use a shared utility/customer network for the rate test. Create a fresh random UUID as the test identifier and include it in the optional review question. Complete the real production challenge and submit ONE normal inquiry to the existing owner mailbox. In browser Network, record only the successful HTTP200, `accepted:true`, time and `X-Contact-Diagnostic-Id`. Do not export its payload/token. If delivery is ambiguous, do not retry automatically.
3. Within the token validity window, use browser Network's resend/replay operation on that exact successful request once. Record HTTP400 and response error `Security verification expired or failed. Please try again.` with its new diagnostic UUID and time. A429/field-error is not replay proof. Keep the request only in the browser; never copy its token to chat/files. If necessary restart the production session with a fresh inquiry after the limiter clears, rather than inventing replay proof.
4. From that same-origin tab's console, run `await fetch('/api/contact',{method:'POST',headers:{'Content-Type':'application/json'},body:'{}'})`. Inspect HTTP400, response error `Please check the fields and complete the security verification.`, time and diagnostic UUID. This invalid empty payload cannot send email or reach Turnstile. Record success/replay/validation in that order as `production.results`, each with `scenario`, `http_status`, `observed_at`, `diagnostic_id`.
5. On only that same operator connection, send the same empty-body request sequentially, at most8times, stopping at the first429. Record numeric statuses and the final observation time. Do not loop across IPs or test customer networks; other IP keys/intake stay enabled. If no429 occurs, record failure and stop; never fabricate limiter evidence. The existing limiter may be eventually consistent.
6. Visually confirm the one UUID-marked inquiry in Zoho Inbox, from `website@neraium.com` to `craig@neraium.com`, subject `Neraium evaluation inquiry`. Record only the test identifier, actual receipt observation time, addresses, subject and visual verification method. Confirm the sender/content are the inquiry just submitted. No actual inquiry text is stored in evidence. This is separate production delivery evidence, not a synthetic receipt.
7. Confirm actual production browser operation with identity, start/completion times (<=20minutes) and results. Record `hostname`, current public `site_key`, `human_operated:true`, `confirmed_by_user:true`, `operator`, `started_at`, `completed_at`, `test_identifier`, `success_accepted:true`, `exact_request_replayed:true`, actual `replay_response_error`/`validation_response_error`, `rate_limit_statuses`, `rate_limit_observed_at`, ordered `results`, and `receipt` with `verified:true`, `method:'Visual verification in Zoho Mail Inbox'`, matching identifier and actual `observed_at`. These values must describe what happened, not a prefilled checklist.
8. Revoke/retire the dedicated verifier and verify every cleanup item in OPERATIONS.md. Capture the after-boundary snapshot, compare it with the before snapshot and independently confirm the entire sanitized evidence digest with the founder. Preserve failed attempts separately. Do not write new data into historical activation evidence or change owner approvals.

Isolated tests establish the same source handler's synthetic failure/recovery, unused-token expiry, validation and dedicated limiter behavior. They do NOT establish production hostname/widget/limiter/mail behavior. The separate production success/replay/validation/429/Inbox checks establish those actual deployment observations. Production equipment/mail delivery is never deliberately failed. Existing code, configuration and security mechanisms remain unchanged.
